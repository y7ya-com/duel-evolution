# Duel sound evidence and integration

`DuelAudioDirector` owns a bounded cue queue and emits paths for `BrowserAudioManager.playEffect`; it does not own/dispose that manager, decode sound, run timers, or retain duel states. Constructor: `(initialSequence = 0, {maxQueuedCues = 64, maxCuesPerSample = 8, muted = false, reducedMotion = false})`.

Feed `enqueue(previousState, nextState)` exactly once for every state fed to `DuelTimeline.enqueue`. After enqueue/advance/skip, call `consumeSample(timeline.sample())`; dispatch each returned cue's `path` once. Call it before acknowledging/clearing model events. The director stores copied cue metadata, so later model acknowledgement cannot remove queued sounds. Multiple commands in one packet retain their distinct ordinals. It rejects out-of-order samples. `reset(sequence)` clears old duel state/counters; `dispose()` releases the queue and forbids further cues.

The **timing policy**, rather than an original timing equivalence claim: sounds are emitted when their packet first appears in the displayed sample, or at acknowledgement if a short/instant batch completed between frames. Existing packet batches can contain several original sequential commands. The current visual timeline does not reproduce all original subcommand phases; original attack swing occurs at battle counter `0x90`, while this director uses attack presentation start. Original exact sound/animation synchronization remains unproven. There are no guessed milliseconds or sound lengths.

Muted cues are consumed permanently; unmuting does not replay old effects. Failed/blocked `playEffect` results likewise must not be retried. Browser activation, gain, decoding limits and voice ownership stay with `BrowserAudioManager`. Explicit timeline skip/overflow suppresses cues completed without being displayed. `setReducedMotion(true)` permits those cues at acknowledgement, with a bounded burst, independently of mute. Keep this flag synchronized with the timeline setting. A later user skip while reduced motion is enabled therefore shares the compressed acknowledgement policy. Queue overflow drops oldest pending cues; per-sample overflow drops excess cues. `counters` exposes emitted/muted/dropped/skipped totals; no cue backlog grows without bound.

ID-to-filename confirmation: the configured archive's `data/etc/se.txt` at offset 437116898, 394 stored bytes / 864 LZSS-decoded bytes lists attack, damage, reborn, life_up, turn_change, battle_turn and card_move at zero-based lines 6, 9, 14, 27, 5, 17, 15. Only the bounded range was read; no sound bytes or generated tables are embedded in source. `client/recomp/audio-slots.md` documents effects as `0x10000000 + line`. Each se.txt line's second column is the original per-file effect volume (0..127): attack 122, damage 125, reborn 125, life_up 126, turn_change 120, battle_turn 125, card_move 122 and, for the cues in the second table below, card_normal_brake 126 (line 8), card_attacked_brake 122 (7), ikenie 123 (12), magic_active 120 (13), chain 123 (26), coin 127 (25), dice 127 (24). `DUEL_SOUND_EVIDENCE` carries it as `volume`, and every cue carries `volume` plus `gain = volume / 127` (`duelSoundGain`). That gain is a proportional scale only: how the original turns the value into DirectSound attenuation (effect play path `0x686e10`) is not verified. The app plays each cue with `BrowserAudioManager.playEffect(cue.path, cue.gain)`, which multiplies the gain into that play's node gain on top of the manager's effect volume; a cue with `delay` (the die) is played that many milliseconds later through a timer in `app.ts`, and dropped if the app was disposed meanwhile.
