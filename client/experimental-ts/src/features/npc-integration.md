# NPC conversation and reward controller

`NpcController` in `npc.ts` owns no DOM, transport subscription, inventory, engine or timers. Construct once per app, wire `onChange` to presentation and route current lobby `WireMessage`s through `receive`. `onStartDuel(id)` should reset the duel model then invoke `GameSession.startNpcDuel(id, activeDeck)`. The callback is invoked only after an affirmative answer. `send(id,data)` must target the same authenticated lobby channel; `onRefreshCollection` should invoke `session.refreshCollection()` after each confirmed grant. Concurrent grants queue a second refresh if necessary.

Public state has `stage`, `npc`, `dialogue`, `result`, `present`, `packs`, `packStatus`, `giftStatus`, `cards`, `giftBits`, `giftCards`, `settlementReceived`, `refreshPending`, `error`. `cards[].id` and `giftCards[]` are **passcodes**, not legacy internal IDs; source `Lobby.cardsResult` and `persist.itemgetResult` encode u32 passcodes. `cards[].isNew` is true when wire flag is 1. Grant receipts alone do not mutate the app's collection; refresh reconciles authoritative ownership.

- `checkEligibility()` performs the original world-initialization `ITEMGET(1,0)` request: 0x5204 with u16 type1/u32 zero. State `eligibility` contains `status`, `refreshing`, confirmed `bits` and `cards`. It returns false while an uncorrelated contact/gift or an existing eligibility request remains pending/uncertain, while a conversation is active, or while an offered pack remains unselected. It permits a new intentional world initialization after a confirmed check. It never retries uncertain delivery. Supply `onRefreshProgress` to refresh authoritative PBIN/NPCBIN after the acknowledgement and before another NPC opens; a receipt can omit entitlement bits. An empty receipt neither grants nor revokes a client-inferred right. `open` rejects with an actionable waiting/uncertain error until check and refresh settle. Ordinary `close()` preserves this eligibility record; hard session reset clears it.

- `open({id,name}, authFlags?, context?: NpcOpenContext)` keeps the old ASK behavior when context is omitted. With context it enters `opening`; `advance()` reads that line before ASK (or greeting with auth flag 0x100). `context.npcRank` is exactly NPCBIN byte `id*4+3`, not wins or a PBIN bit. Zero shows line0 and sends ITEMGET type4 once; nonzero shows line5. Unknown rank shows an explicit unavailable line and sends nothing. `firstContactStatus` tracks the empty `0x5205` acknowledgement separately from gifts. Pending/uncertain contact blocks duel acceptance and opening another conversation, avoiding collision with later uncorrelated gift receipts. No item/card receipt or inventory refresh is invented. Confirmed contact is remembered for this controller/session, so reopening with a stale zero snapshot uses line5 without resending. `disconnected()` marks an unresolved contact uncertain; late empty acknowledgement resolves it without replay.
- `answer(true)` starts the duel once. `answer(false)` opens original greeting line 10; missing greeting text uses the original `…?` fallback.
- `afterDuel(1|2|3)` accepts the server model result once for the active NPC, before or after lobby handoff. It opens `after-duel`. Pack/present messages arriving while `duel` are retained.
- `advance()` closes greeting. After the result dialogue, it waits for settlement `0x4800`, then chooses WON line 0x45 / LOST line 0x4a for server present kind 1, ITEM line 0x4f for kind 2, or ends when no gift was announced. After reading the gift dialogue it sends exactly one `0x5204` (u16 type3, u32 zero). The `0x5205` receipt confirms gift bits/cards; empty receipts are confirmed empty, never invented rewards.
- `selectPack(pack)` requires a server-offered `0x4800` pack and a result. It sends one `0x4802` u16 pack and waits for `0x4803` (u32 result, repeated u32 passcode/u8 new). Repeated clicks/receipts do not grant or refresh twice. Failure becomes `failed`; send failure becomes `uncertain`. Neither automatically replays.
- `refreshCollection()` safely reconciles inventory; retrying it never sends a claim. `disconnected()` preserves receipts and marks pending mutations uncertain. Keep the controller through a resumable tunnel interruption. `close()` dismisses idle/done presentation while retaining contact history, refusing unresolved contacts, pending rewards and unselected offered packs. Use it for ordinary modal dismissal. `reset()` belongs to logout, character change, or discarded session, not ordinary resume; detach old transport callbacks before reset. `dispose()` makes subsequent methods inert and invalidates asynchronous work.

Source behavior comes from `client/src/Lobby/yo2NpcListMenu.cpp` (`stepAsk`, `stepAsking`, `stepGreet`, `openAfterDuel`, `stepAfterDuel`, `stepTalkDone`) and actual server `duelfin.ts`, `npcRules.ts`, `lobby.ts`, `shop.ts`, `persist.ts`. `0x4237` is the authority for a gift; account update `0x4140` does not prove a reward and is intentionally not interpreted by this controller. `0x4804` is not part of this server's NPC pack claim route.

## Original dialogue data

`NpcDialogueCatalog` (`../npcs/dialogue.ts`) accepts `{version:1,lines:{[npcId]:{[line]:{text,textId,style}}},presentTexts?:{[textId]:text}}`. Install parsed JSON, supply `resolveLine:(npc,line)=>catalog.resolve(npc,line)` and `resolvePresentText:id=>catalog.resolveText(id)`. Only the fifteen recovered eligibility text IDs are admitted in `presentTexts`, including empty trailing lines. Clear on app disposal. Exact private strings never appear in tracked source. `tools/npc-data.mjs <ignored-output.json> <fuki_index.csv> <yo2text_e.idx> <yo2text_e.bin>` joins separately extracted original files, preserving per-line text ID/style and the three independent five-string eligibility blocks. The generator rejects tracked, unignored, symlinked, outside-repository outputs and oversized inputs, and refuses overwrite. Use `public/npc-data.json`, which the root owner ignores. Runtime catalog validation is atomic and bounded.

Actual configured-host extraction used `ArchiveReader` via a bounded HTTP/2 curl fetch adapter: 12-byte header, 5,211,260-byte directory, then only fuki_index.csv (16,850 stored), text index (83,299 stored), text bin (117,191 stored). All ranges passed ArchiveReader Content-Range/body-length validation; no whole archive request. Generated ignored local catalog validates 98 NPCs. The tracked generator itself reads extracted files and does not perform network downloads.

## Limits and evidence

The original result-opening `duelResultLine` at PE 0x007918c0 was inspected statically. It depends on an additional legacy result category, both LP snapshots, turn counter +1 and remaining deck counts, not just WIN/LOSE. The category-to-current-server-event mapping remains unconfirmed. Supply `resultLine(result)` only when that mapping is independently established; the default result-opening dialogue explicitly says original dialogue unavailable. Missing non-greeting lines are also explicit placeholders. The normal pre-question opening and first contact are implemented with optional authoritative context. The three special branches are source refusal dialogues when the character lacks an eligibility right, not unconditional gifts. `npcOpeningPresent(id)` exposes their recovered predicates: NPC 0x36 -> PBIN 0x250 / text base 0x63e2; 0x42 -> 0x251 / 0x655e; 0x4b -> 0x252 / 0x6aae. The boolean `context.specialPresentDone` must reflect that completion bit; only true permits normal opening. False shows the recovered five-string refusal dialogue when supplied; unknown progress remains explicitly unavailable. Continue closes that refusal without asking for a duel or claiming a gift. Eligibility is first checked through the verified world initializer request and then observed in refreshed PBIN, so newly earned rights allow the normal opening on a later interaction. A missing completion bit is not proof of an available grant. `presentFor` passes five adjacent text IDs to `waistUpSayPresent`; these are independent string-table entries, not ordinary fuki lines. Source `npcPresentDone` PE 0xa56060 calls NPC classification 0xa55cd0, then tests bits 0x250/251/252; the three IDs were verified through its jump table. No private strings were embedded. Raw original text is retained; this controller does not implement the old balloon renderer, inline commands, dynamic speaker substitutions, text paging, voice or style rendering.

Focused unit tests cover source line/stage transitions, duplicate clicks/receipts, malformed/refused grants, uncertain sends, refresh retries/queuing, reset/dispose and stale asynchronous callbacks. `npc-server.test.ts` drives the real server/World, native OCGCore, typed reducer and encoded legal client choices to natural win/loss. The gift threshold fixture starts with four historical wins; the tested game's engine supplies the fifth. No engine outcome command is injected. Tests also exercise actual pack claim, exact server trunk delta, inventory refresh, real policy refusal after consumption, and pending/confirmed tunnel disconnect/resume. These focused fixtures do not establish complete NPC/gameplay parity.

The legacy mutation protocol has no per-claim idempotency key. This controller ensures one outbound attempt per entitlement in its current lifetime and relies on server pending-package consumption. Across process loss, an uncertain claim must be reconciled from server inventory; exactly-once delivery or reconstructing every lost receipt is not claimed. Other lobby consumers must not independently send the same item/pack claim while this controller owns it.

## Parent wiring and receipt limits

Retain per-character snapshots only after exact-length validation: `0x3114` PBIN = 128 bytes, bit `(pbin[bit >> 3] >> (bit & 7)) & 1`; `0x4234` NPCBIN = 512 bytes, NPC row `[wins, losses, draws, rank/chainStep]` at `4*id`. Pass `npcRank` only once NPCBIN is loaded; pass `specialPresentDone` only once PBIN is loaded. Do not zero-fill missing snapshots. Refresh/update progress after character selection and authoritative `0x4140` updates as supported by the session. The controller's contact cache is an original-style local seen marker, not a replacement for persistence. Render `opening` with Continue and surface `firstContactStatus` pending/uncertain. Use `close()` for modal dismissal, reset only on hard session/character changes with old transport listeners detached.

Current server `persist.onItemget(kind=4)` sets byte3 to1 only when zero and NPC id is in1..127, always returning exactly two zero u16 counts, even for an invalid NPC id. Thus confirmed means an empty acknowledgement, not a newly verified right, grant, or a distinguishable refusal. The controller validates rank/id before sending; malformed/nonempty contact receipts remain unresolved. A lost receipt with no later acknowledgement remains uncertain; no automatic resend is attempted. The wire has no correlation IDs, so arbitrary duplicate/delayed receipts across a new hard session cannot be distinguished. Never route another consumer's ITEMGET while this controller has an outstanding contact/gift.

## World-initialization request evidence

Static inspection of the supplied original PE, never executed, confirms CAreaMapScene RTTI at vtable 0xbf0e60. Its CEasyTask onInit slot3 points through thunk 0x40eaca to 0x9fcca0. After creating world UI, address 0x9fdba6 pushes param0/type1; call 0x9fdbb0 reaches ITEMGET thunk0x40a317 and implementation0x6cf000, which sends0x5204. This is the sole type1 ITEMGET call in the static executable. `tests/npc-source.test.ts` validates those bytes when the optional original executable is available; it never launches the binary.

The supplied PE's SHA-256 is `d25d4b135602eafe9db1a709ac5d2367295ba1dad084366d37a1a7577021e613`; no executable or private dialogue text is copied into tracked evidence.

Actual server policy is `persist.onItemget(kind=1)` and `challengeRightsDue`: NPC75/bit594 is available without historical wins; NPC54/592 requires five wins against one of6/7/9; NPC66/593 requires five wins against one of31/32/33. These are server rules, not duplicated client eligibility decisions. The focused real-server test supplies fixture history at threshold boundaries, sends the real request, refreshes exact128-byte PBIN/512-byte NPCBIN, verifies the observed rights and unchanged trunk, and verifies an empty repeated acknowledgement does not erase owned rights. Existing server `h_getpbin` clears pending presentation packages: invoke progress refresh only after this owned ITEMGET acknowledgement and serialize it against NPC grants, as this controller does.

The original PRESENT stage waits on the general ITEMGET completion flag; the missing world-initialization check caused the previous new-client fallback to strand these interactions. The five strings contain refusal text, so there is no source-backed special reward-acceptance choice to invent. Full original balloon animation/substitution remains a presentation gap.
